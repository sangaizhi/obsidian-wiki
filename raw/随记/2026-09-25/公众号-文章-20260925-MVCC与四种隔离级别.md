# 十万个why：明明 MVCC 已经实现了无锁读，为什么 MySQL 还需要四种隔离级别？

- **标签**：`MySQL` `InnoDB` `MVCC` `事务隔离级别` `并发控制`

---

## 一句话结论

**MVCC 提供能力，隔离级别定义策略，两者不是同一层面的东西。**

MVCC 只是提供了"读历史版本"的机制，但"该读哪个历史版本"由 ReadView 的创建策略决定，而这个策略正是隔离级别在控制的东西。

---

## 1. MVCC 到底做了什么

InnoDB 每一行数据都有两个隐藏字段：

- `DB_TRX_ID`：最后修改这行数据的事务 ID
- `DB_ROLL_PTR`：指向 undo log 中这行的上一个版本

每次 UPDATE，旧版本不覆盖，而是写入 undo log，通过指针串成一条**版本链**。

事务执行 SELECT 时，InnoDB 不直接读当前版本，而是生成一个 **ReadView 快照**，用它判断版本链上哪个版本对当前事务**可见**。

ReadView 记录了当前所有活跃（未提交）的事务 ID 列表，判断规则：

| 版本 trx_id 情况 | 可见性 |
| --- | --- |
| 在我事务开始前已提交 | ✅ 可见 |
| 在我之后才开始的事务 | ❌ 不可见，沿版本链往下找 |
| 还在活跃列表里（未提交） | ❌ 不可见，继续往下找 |

看起来一切完美：读历史版本、写当前版本，读写完全不冲突。

---

## 2. 那为什么还需要隔离级别？

因为**"我应该看到哪个版本"**这个问题，不同业务场景答案不一样。

MVCC 只提供读历史版本的机制，具体读哪个版本取决于 **ReadView 的创建策略**。

### READ COMMITTED（RC，读已提交）

- **每次 SELECT 都新建一个 ReadView**
- 两次 SELECT 之间若其他事务提交了修改，第二次就能读到新数据 → 即**不可重复读**
- 表现：同一事务里两次读同一行，结果不一样

### REPEATABLE READ（RR，可重复读）

- **整个事务只创建一次 ReadView**（第一次 SELECT 时创建）
- 后续所有 SELECT 复用同一快照
- 不管外面怎么变，事务内看到的数据永远一致

> **关键点**：RC 和 RR 用的是**完全一样的 MVCC 机制**，区别仅仅是 ReadView 什么时候创建——一个每次读都重拍快照，一个整个事务只拍一次。就这一个时机差异，造成两种截然不同的隔离效果。

---

## 3. READ UNCOMMITTED 为什么不用 MVCC？

RU 的语义是"可以读到其他事务还没提交的修改"。

既然连未提交的都能读，直接读版本链最上面的当前版本就完事，根本不需要创建 ReadView 去过滤。

MVCC 的意义在于**屏蔽不该看到的版本**；如果你什么都想看，那 MVCC 就是多此一举。

> 所以 RU 不是"不能用 MVCC"，而是**用了也没意义**。

---

## 4. SERIALIZABLE 为什么也不用 MVCC？

SERIALIZABLE 走另一个极端，**所有读操作都加共享锁**。

```sql
-- SERIALIZABLE 级别下，普通 SELECT
SELECT * FROM user WHERE id = 1;

-- 会被自动转换成
SELECT * FROM user WHERE id = 1 LOCK IN SHARE MODE;
```

读也加锁意味着读写之间互相阻塞，与 MVCC 的设计目标（读写不阻塞）完全背道而驰。

> SERIALIZABLE 放弃了 MVCC 的并发优势，换来最强的一致性保证：事务之间完全串行执行。

---

## 5. 一张图看清关系

```
                    一致性强度 ↑
  READ UNCOMMITTED  ── 读版本链最新版（不用 ReadView）
  READ COMMITTED    ── MVCC，每次 SELECT 新建 ReadView
  REPEATABLE READ   ── MVCC，事务内只建一次 ReadView
  SERIALIZABLE      ── 不加 MVCC，读也加共享锁，全串行
```

（原文配图：MVCC 能力 ↔ 隔离级别策略的对应关系）

## 6. MVCC 管不了写

MVCC 只解决**读**的问题（快照读），**写**的时候依然需要锁。

InnoDB 里有两种读：

- **快照读（Snapshot Read）**：普通 SELECT，走 MVCC，不加锁
- **当前读（Current Read）**：`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` / `INSERT`，必须读最新版本（否则 UPDATE 可能基于过时数据修改），不走 MVCC，走行锁

```sql
-- 快照读：走 MVCC，可能读历史版本，不加锁
SELECT * FROM account WHERE id = 1;

-- 当前读：加排他锁，读最新版本
SELECT * FROM account WHERE id = 1 FOR UPDATE;

-- 当前读：UPDATE 内部先读取当前最新值
UPDATE account SET balance = balance - 100 WHERE id = 1;
```

InnoDB 在 RC / RR 下的实际策略：

- **读用 MVCC** → 无锁快照读，不阻塞写
- **写用行锁** → 互斥，保证数据安全

读写之间不冲突（读历史版本、写当前版本），写写之间通过行锁互斥。

> **这才是 InnoDB 并发性能好的真正原因**：不是单靠 MVCC，也不是单靠锁，而是两者的**分工配合**。

---

## 7. 说在最后

- MVCC 是一个底层并发控制工具，解决"读操作如何不加锁地获取一致数据"。
- 但一致到什么程度，是业务层面的选择，由隔离级别控制：
  - RC：只看已提交的最新数据
  - RR：整个事务期间数据不变
  - RU：连未提交的都能看
  - Serializable：读也加锁，保证绝对串行
- **MVCC 提供能力，隔离级别定义策略，它们不是同一层面的东西。**

---

## 我的记忆钩子

1. MVCC = 机制，隔离级别 = 策略（ReadView 何时创建）。
2. RC vs RR 唯一区别：ReadView 是每次 SELECT 建还是整个事务建一次。
3. RU 不用 MVCC（要读未提交就直接读最新版）；Serializable 不用 MVCC（读也加锁，放弃并发）。
4. 读走 MVCC 无锁、写走行锁互斥 —— 分工配合才是 InnoDB 快的原因。
