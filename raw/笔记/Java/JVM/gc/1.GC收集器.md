### 一、什么垃圾收集器
    JVM 垃圾收集器，就是收集JVM的中的垃圾数据的器物。
### 二、为什么要有垃圾收集器
    因为在程序运行的过程中，会不断的产生新的对象和数据，但是这些数据可能不会及时的被销毁，一直存在于内存中；随着程序的运行，这部分数据(不再被任何途径使用的对象)可能会越来越多。而我们清楚，内存是一个比较珍贵的系统资源。JVM 为了让内存资源不会被没必要的浪费，就在虚拟中提供了一些（可能不止一个，可以自主选择）垃圾收集器。这些垃圾收集器能够使用不同的算法回收程序运行后的垃圾数据。实际上，虚拟机规范中对垃圾收集器的实现没有任何规定，因此，不同的厂商、版本的虚拟机所提供的垃圾收集器都可能会有很大差别，并且一般都会提供参数供用户根据自己的需求组合出个年代所使用的收集器。
### 三、垃圾收集器的主要工作
    垃圾收集器的主要工作是回收JVM中已经不再被任何途径使用的对象所占的内存，其主要回收的内存区域是Java堆和方法区（程序计数器、虚拟机栈、本地方法栈三个区域是随着线程而存在的，所以在线程或者方法结束时，内存自然就被回收了）。

### 四、垃圾收集器的种类
   ![Hotspot虚拟机的垃圾收集器](https://blog-1253360328.cos.ap-guangzhou.myqcloud.com/image/jvm_gc_collector.png)
      
    上图展示了7种不同分带的收集器，如果两个收集器之间存在连线，就说明他们可以配合使用。虚拟机所处的区域，则表示它是属于新生代收集器还是老年代收集器。

#### 4.1、Serial 收集器
      Serial 是最基本、最老的收集器。在 JDK 1.3.1 之前是新生代收集器的唯一选择。
      Serial 是一个单线程的收集器。这里的单线程不是指 Serial 只会使用单个的 CPU 或者一条线程去执行垃圾收集工作。
      更重要的是指它在执行垃圾收集，会暂停其它的工作线程(Stop The World)，直到他收集完成。

#### 4.2、ParNew 收集器
	      ParNew 其实是 Serial 收集器的多线程版本，除了使用多线程进行垃圾收集外，其余行为包括 Serial 收集器可用的
      所有控制参数(eg: -XX:SurvivorRatio、-XX:OretenureSizeThreshold、-XX:HandlePromotionFailure)、收集算法、Stop the
      world、对象分配规则、回收策略都与 Serial 收集器完全一样。
	      ParNew 虽然对比 Serial 收集器没有太多的创新，但是它还是运行在Server 模式下的虚拟机中首选的新生代收集器。
      其中一个很重要的原因就是，在 JDK 1.5 及之后， 除了 Serial 之外，只有它能够与CMS(Concurrent Mark Sweep：在JDK 1.5 版本
      时推出)收集器配合使用。即使这样，ParNew收集器也是使用-XX:+UseConcMarkSweepGB 选项后的默认新生代收集器，也可以使用
      -XX:UseParNewGC 选项来强制制定它。    

      注意：在单 CPU 环境下，ParNew 收集器的效果绝对不会比Serial 好。在双CPU下，都不能百分之百的比 Serial 高效。在更多的CPU数
      量的情况下，ParNew的效果还是比Serial好的。ParNew 默认开启的收集线程数与CPU的数量相同，可以使用 -XX:ParallelGCThreads
      参数来限制垃圾回收的线程数。

#### 4.3、Parallel Scavenge 收集器
 	     Parallel Scavenge 是一个新生代收集器，使用的复制算法，也是并行的多线程收集器。
          Parallel Scavenge 收集器的特点就是它的关注点，它关注并不是如何缩短垃圾收集工作线程停顿的时间，而是如何达到一个可
     控制的吞吐量（CPU用于运行用户代码的时间与CPU总消耗时间的比值）。所以Parallel Scavenge 适合使用在后台运算而不是太多交
     互的任务。
          Parall Scavenge 收集器提供了两个参数用于精准的控制吞吐量，分别是控制最大垃圾收集停顿时间的
     -XX:MaxGCPauseMillisß和直接设置吞吐量大小的 -XX:GCTimeRatio 参数。
		      -XX:MaxGCPauseMillis: 一个大于0 的毫秒数参如果设置过小，就会导致每次回收的空间较小，直接导致垃圾收集的频率更
          高，造成吞吐量的下降。
		      -XX:GCTimeRatio：大于0小于100的整数，表示的是垃圾收集时间占总时间的比率，也就是吞吐量的倒数。
		由于关注的是吞吐量，所以Parallel Scavenge 也被称之为“吞吐量优先”收集器。此外，Parallel Scavenge 还有一个参数
    -XX:UseAdaptivePolicy,这个参数的主要作用就是不需要手动的制定新生代的大小（-Xmn）、Eden、Survivor比例。对象晋升老年代
    的年龄等细节参数，虚拟机会根据当前系统的运行状态收集性能监控信息，动态的调整这些参数来提供最合适的垃圾收集停顿时间或者最
    大的吞吐量。此外，在JDK 1.6之前，Parallel Scavenge 收集器的地位比较尴尬。原因就是如果新生代选择了Parallel Scavenge
    收集器，老年代处理Serial Old收集器（下面会介绍）之外别无选择。而 Serial Old 收集器在Server模式下应用性能的不足，所以
    这种组合模式ParallelScavenge 和 Serial Old）在老年代很大并且硬件资源高级的情况下，吞吐量就显得不尽人意。这主要是
    Serial Old 是单线程的收集器的缘故。

#### 4.4、Serial Old 收集器
        从名称上可以看出这个收集器是Serial收集器的老年代版本，所以同样是一个单线程的收集器，使用是标记-整理算法，主要意义也是用于Client模式下的虚拟机使用。当然，在Server模式下也是可以使用的，主要有一下两大用途：
        1）、用于JDK 1.5及之前的版本中与Parallel Scavenge收集期搭配使用；
        2）、作为CMS收集器的后备预案，在并发收集发生时使用。

#### 4.5、Parallel Old 收集器
        Parallel Old同样是Parallel 收集器的老年代版本，使用的也是标记-整理算法。这个收集器在JDK 1.6 版本以后才开始提供。在介绍 Parallel Scavenge 收集器时提到过 Parallel Scavenge 与Serial Old 收集器组合在Server端使用时，会导致机器设备的资源得不到充分使用，导致吞吐量不够给力。所以，在Parallel Old 出现后，‘吞吐量优先’的收集器终于有了名副其实的组合。在比较重视吞吐量及CPU资源的场合，都可以优先考虑Parallel Scavenge 和 Parallel Old收集器的组合。

#### 4.6、CMS 收集器（Concurrent Mark Sweep）
        CMS 收集器是一种以获取最短回收停顿时间为目标的收集器。比较适合B/S这种重视响应速度的服务端应用。
        从名称上可以看出，CMS 收集器采用的是“标记-清除”算法，实现的过程比较复杂，可以分为一下四步：
            1. 初始标记（CMS initial mark）
                初始标记仅仅只是标记 GC Roots能直接关联到的对象，速度快。当然 Stop The World 还是存在。
            2. 并发标记（CMS concurrent mark）
                并发标记就是 GC Roots Tracing 的过程
            3. 重新标记（CMS remark）
                重新标记是为了修正个并发标记期间因用户程序继续运作而导致标记产生变动的那一部分对象的标记记录。这个阶段的停顿时间一般会比初始标记阶段稍长，但远比并发标记的时间短。
            4. 并发清除（CMS concurrent sweep）

        在这个四个阶段中，并发标记和并发清除的时间都比较长，但是这两个过程都可以和用户线程一起工作，所以，从总体上说，CMS 收集器的内存回收过程是与用户线程一起并发执行的。
        CMS 收集器的缺点：
            1): 对CPU资源敏感
                在并发期间，会占用一部分线程而导致应用程序变慢
            2): 无法处理浮动垃圾，
                浮动垃圾是用户线程在垃圾收集器收集时产生的垃圾。
            3): 由于基于标记-清除算法，所以会有大量的空间碎片产生。

### 4.7、G1 收集器
        在 JDK 1.6 版本中就有提供Early Access 的版本供开发人员实验、试用，但是，知道 JDK 1.7 开始才开始商用。
        G1 之前的收集器都只是回收新生代或者老年代，但是 G1 不同，它既能回收新生代，也能回收老年代。
        G1收集器的特点：
            1. 并行与并发
                G1 收集器能够充分的利用多CPU、多核的硬件优势，使用多个CPU（CPU或者CPU核心）来缩短 Stop The World 的时间。部分其他的收集器需要停顿用户线程执行GC动作，但是 G1 可以并发的执行用户线程。
            2. 分代收集
                G1 收集器仍然保留着分代的概念，但是G1能够独立管理Java堆（新生代和老年代），可以采用不同的方式去处理新创建的对象、已经存活一段时间的对象和一些旧对象，已达到更好的手机效果。
            3. 空间整合
                G1 从整体上看，采用的是"标记-整理"算法，从局部上（两个 Region）看采用的是复制算法实现。根据这两个算法的特点，都不会产生空间碎片，收集后能够产生比较连续的内存空间。
            4. 可预测的收集
                G1 处理能够通过并行来降低垃圾收集的时间外，还能够建立可预测的停顿时间模型，能够让使用者在指定长度的时间范围内，停顿的时间不超过某个值。
        G1 收集器采用了把内存“化整为零”的思路。大体的思想就是：把 Java堆的内存划分为多个大小相等的独立区域（Region）,当然还保留着新生代和老年代的概念，它们不在物理分割，都只是某部分Region的集合（Region可以不连续）。
        G1 收集器之所以能够建立可预测的停顿时间模型，主要是因为它的每次垃圾收集都是有计划的，能避免每次都在Java 堆中进行全区域的扫描、收集。在G1中，G1会 会记录跟踪每一个Region的回收价值（回收价值通过回收所获得空间及回收所花费的时间计算），然后维护一个优先列表，按回收价值的大小来标记各个Region。这样，在下一次GC时，就能够根据允许的GC时间来回收价值较大的Region，从而实现在有限的时间获得最高的回收效率的目的。
        上面提到 G1回收时是按 Region 为单位进行回收的，但是存在一个问题，一个Region不可能是完全独立的，Region 中的对象并不是只能被本 Region 中的对象引用，可能被 Java 堆中任意地方的对象引用。那么，在做可达性分析的时候，难道就需要扫描整个Java堆。在 G1 收集器中，Region 之间的引用以及新生代和老年代对象之间的引用，都采用 Remembered Set 来避免全堆扫描的。G1 中每一个 Region 都有对应的 Remembered Set,当虚拟机发现程序在对 Reference 类型的数据进行写操作时，会产生一个 Write Barrier 暂时中断写操作，随后判断 Reference 引用的对象是否处于不同的Region中（在分代的例子就是检查老年代中的对象是否引用新生代中的对象）。如果是，就通过 CardTable 把相关的引用信息记录到被引用对象所处的 Region 的 Remembered Set中。在进行内存回收时，就会把 Remembered Set 中的对象加入到 GC Roots 根节点的枚举范围中。 这样既可以保证不进行全堆扫描也不会有遗漏。

        G1 收集器的大致步骤：
            1. 初始标记(Initial  Marking)
            2. 并发标记(Concurrent Marking)
            3. 最终标记(Final Marking)
            4. 筛选回收(Live Date Counting And Evacuation)


**并发和并行**
        并行（Parallel）：指多条垃圾收集线程并行工作，但此时用户线程仍然处于等待状态。
        并发（Concurrent）：指用户线程与垃圾收集线程同时执行（但不一定是并行的，可能会交替执行），用户程序继续执行，而垃圾收集程序运行与另一个CPU上。
