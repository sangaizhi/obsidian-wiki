## 🎯 视频核心内容——CLAUDE.md 三步优化法

### 问题：CLAUDE.md 为什么会越写越蠢？

当 CLAUDE.md 增长到 **200 行以上**时：
- 📏 上下文窗口被大量规则描述占用
- 🔄 规则间互相覆盖、冲突
- 🤖 AI 反而变笨——"加东西只会让它越用越蠢"
- 🧠 难以维护，新规则和旧规则打架

### 核心方法论：三步走

```mermaid
flowchart LR
    A["① 根文件做薄<br/>&lt;60行"] --> B["② 按关注点拆分<br/>.claude/rules/"]
    B --> C["③ /memory 逐条验收"]
    C --> A
```

---

### 第一步：根文件做薄（< 60 行）

**目标：** 把 `CLAUDE.md` 压缩到 60 行以内，只保留：
- ✅ 项目概览（一句话说清这个项目是干啥的）
- ✅ 核心约束（必须遵守的底线性规则）
- ✅ 技术栈概述（语言、框架、关键依赖）

**舍弃：**
- ❌ 具体的编码风格细节 → 移到 rules 目录
- ❌ 团队流程说明 → 移到 rules 目录
- ❌ 过时的旧规则 → 直接删除

**Why 60 行？**
- 确保 AI 能完整读完且记住
- 减少 Token 消耗
- 根文件越薄，越容易被认真对待

---

### 第二步：按关注点拆到 `.claude/rules/`

将规则按主题拆分到独立的文件中：

```
.claude/rules/
├── coding-style.md      # 编码风格
├── testing.md           # 测试规范
├── git-commit.md        # 提交信息规范
├── architecture.md      # 架构决策
├── review.md            # 代码审查标准
├── dependencies.md      # 依赖管理
└── memory/              # 从 /memory 同步
```

**好处：**
- 🎯 每个文件专注一个话题
- 📖 AI 按需加载，不占满上下文
- 🔧 修改不影响其他规则
- 👥 适合团队协作分工维护

---

### 第三步：用 `/memory` 逐条验收

HumanLayer 的 `/memory` 命令用于：
- ✅ 验证每条规则是否被 AI 正确理解
- ✅ 检查规则是否与项目实际工作流一致
- ✅ 标记过时或冲突的规则
- ✅ 确保瘦身后的 CLAUDE.md 没有丢失关键信息

**验收流程：**
1. 对每条拆出去的规则，运行 `/memory test <rule-name>`
2. 确认 AI 能根据拆分的规则正确执行任务
3. 定期复查，清理不再适用的规则

## 📊 CLAUDE.md 瘦身前后对比

| 维度 | 优化前（200+ 行） | 优化后（<60行 + rules） |
|------|-----------------|----------------------|
| **根文件大小** | 200+ 行，臃肿 | <60 行，精炼 |
| **规则组织** | 单一文件，杂乱 | 按主题拆分，清晰 |

| **维护难度** | 改了怕影响其他 | 独立修改，互不干扰 |
| **AI 理解度** | 容易遗漏或冲突 | 精准理解，执行正确 |
| **团队协作** | 合并冲突频繁 | 各自维护自己的规则 |

## 💡 核心观点提炼

> **「CLAUDE.md 写到几百行，再加东西只会让它越用越蠢。」**

该视频的受众定位：
1. **Claude Code 用户** — 正在或即将使用 AI 编程助手的开发者
2. **提示词工程师** — 需要设计高效项目上下文
3. **技术团队负责人** — 制定团队 AI 协作规范

**深层洞察：**

这段内容的精妙之处在于它指出了 **AI 上下文管理的一个反直觉现象**：你以为写得越多 AI 越懂你，实际上规则越多 AI 越容易"迷失"。这和人类认知的"选择悖论"异曲同工——选项太多反而做不出好决策。

HumanLayer 的"三层架构"（根文件 → 拆分规则 → 验收）本质上是一种 **Context Engineering** 的最佳实践，将 Claude Code 的项目指令从"杂乱的百科全书"重构为"精炼的索引 + 按需加载的模块"。
