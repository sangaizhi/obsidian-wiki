# 概念：工具调用与执行

## 定义

工具调用是 Agent 将大模型的决策落地为实际操作的能力层。大模型负责"思考"，工具调用负责"动手"——没有工具调用，Agent 只是一个会说话的聊天机器人。

## 两种主流路线

### 路线一：极简 CLI 工具集（OpenClaw 模式）

核心只有 **4 个工具**，遵循 Unix 哲学：

| 工具 | 用途 | 说明 |
|------|------|------|
| Read | 读取文件 | 获取上下文信息 |
| Write | 写入文件 | 创建或修改文件 |
| Edit | 编辑文件 | 精确修改已有文件 |
| Bash | 执行命令 | 运行 CLI 程序、操作系统操作 |

**优势**：
- System prompt 极短，Token 消耗少
- 覆盖几乎所有操作系统级别的任务
- Agent 不依赖预构建工具，通过 CLI 自行扩展能力

**代价**：
- 需要更强的模型能力来"从零写工具"
- 推荐使用 Claude Opus 等高能力模型

### 路线二：MCP 协议（Anthropic 标准）

MCP（Model Context Protocol）是 Anthropic 提出的工具协议标准，多数 AI Agent 框架集成此方案。

**优势**：
- 标准化协议，生态丰富
- 预构建工具集，开箱即用

**代价**：
- 协议层开销，增加复杂度
- 依赖外部预构建工具

### OpenClaw 的反 MCP 立场

OpenClaw 故意不支持 MCP，创始人认为 CLI/Unix 才是真正能 scale 的方案。对于需要 MCP 的场景，通过内置的 `mcporter` skill 桥接。核心观点：**强制 Agent 自己扩展能力**，而非消费预构建的工具集。

## MCP 实战案例：日志平台

得物技术的日志诊断实践展示了 MCP 在企业级场景中的应用模式：

### 日志平台 MCP 架构

- **传输协议**：SSE（Server-Sent Events）长连接
- **鉴权流程**：secretKey → acquireTokenTool → accessToken（1小时有效，最多5个同时存在）
- **核心工具**：logsQuery / logSqlQuery / countLogTool / logFields
- **queryString 语法**：精确匹配（=）、模糊匹配（≈）、AND/OR/NOT 连接符

### MCP + Skill 组合

> **"MCP 给数据，Skill 给流程"** — MCP 解决"怎么拿到日志"的问题，Skill 解决"怎么分析日志"的问题。

## Agent 工作区文件结构

工具调用的执行环境以文件系统为基础：

```
workspace/
├── AGENTS.md          # Agent 定义（身份、行为规则）
├── SOUL.md            # 人格指令（不可变内核）
├── USER.md            # 用户信息与偏好
├── MEMORY.md          # 长期记忆存储
├── HEARTBEAT.md       # 心跳配置（定时任务）
├── memory/            # Daily Logs 目录
│   └── YYYY-MM-DD.md
├── skills/            # 本地技能目录
└── sessions.json      # 会话存储
```

所有配置为纯文本文件，人类可直接编辑。

## 执行闭环

典型的工具调用路径：

1. **感知**：接收用户输入和环境状态
2. **决策**：大模型分析后决定调用哪个工具
3. **执行**：通过工具执行实际操作（读文件、写文件、执行命令等）
4. **反馈**：将执行结果返回给模型，评估是否需要下一步
5. **循环**：未完成则继续决策-执行-反馈，直到任务闭环

## 工具选择与并发执行

Agent 工具链可以进一步拆成 Tool Selection 和 Tool-Calling：前者决定“该用哪个工具”，后者负责把参数结构化并执行。Claude Code 的实现细节表明，并行工具调用并不是简单同时启动所有命令，而是需要判断工具调用是否安全、是否会互相影响，以及结果是否能按 `tool_use` 顺序回传。

其中 `StreamingToolExecutor` 会在流式响应的工具块结束后立即启动可执行工具；`isConcurrencySafe(input)` 用于判断是否允许并发。Bash 等有副作用的命令更容易触发串行或失败中断策略。

## 关键设计原则

- 工具越少，system prompt 越短，Token 消耗越低
- Agent 应有自我扩展能力——遇到不会的操作时自行编写工具
- CLI 是最通用的接口层，不需要为每个服务写独立集成
- 工具执行结果应只保留关键片段，避免海量原始数据塞入上下文

## Claude Code 工具设计哲学：高/中/低层搭配

Claude Code 的工具设计展示了成熟的工具分层思想：**全都要，并且合理搭配**。核心原则是 **使用频率 × 成功率** 的权衡。

### 三层工具架构

| 层次 | 示例 | 设计目的 | 与 Bash 的关系 |
|------|------|---------|--------------|
| **高层** | WebFetch, Agent, Skill | 封装复杂多步骤，模型只需提供输入 | 将 curl→解析→编码等步骤封装，比 Bash 更稳定 |
| **中层** | Read, Write, Edit, Glob, Grep | 高频文件/代码操作，专门优化 | 搜索是高频动作，Bash 调用 grep 容易记错参数 |
| **低层** | Bash | 万能工具，覆盖无专用工具的场景 | 基础能力 |

### 为什么要有专门工具？

已有通用 `Bash` 工具，为什么还单独实现 `Grep`、`WebFetch`？

> "你会希望手里有什么工具来解题？答案取决于你自身的能力。纸笔是最基础的配置，但你会受限于手算能力。计算器更好，但你得会用它的高级功能。最快、最强的选项是计算机，但前提是你知道如何写代码并执行代码。" — Thariq (Anthropic)

**专门工具 = 把模型不擅长的步骤封装成稳定模块**，让模型专注于自己擅长的事（推理与决策）。

### 渐进式信息披露

不给模型一次性展示所有信息，而是提供搜索/浏览工具，让模型自主决定探索路径。这更接近人类开发者的工作方式——边看边找，逐步深入。
