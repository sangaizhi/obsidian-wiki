# 概念：上下文工程

## 定义

上下文工程是面向 AI 应用的记忆管理和信息选择策略。它决定哪些信息应该进入模型上下文，哪些信息应该摘要、丢弃或延后加载。

## 解决的问题

- 长对话变笨：上下文过长后，模型可能遗漏前文、答非所问或胡编。
- 成本变高：每次请求都携带大量历史，会增加 Token 消耗。
- 信息过载：无关内容越多，模型越难抓住当前任务重点。

## 设计原则

- 只加载当前任务所需的信息。
- 历史对话保留摘要，而不是保留完整流水账。
- 工具结果只截取关键片段。
- 任务完成后的中间信息及时归档，避免长期污染上下文。

## 实用口诀

- 不用的信息不加载。
- 记结论不记流水账。
- 只看关键片段不看全文。

## 最佳实践：CLAUDE.md 三步优化法

Context Engineering 在 AI 编程工具中的具体应用——CLAUDE.md 优化：

**第一步：根文件做薄（< 60 行）**
只保留项目概览、核心约束、技术栈概述。去掉编码风格、团队流程等细节。

**第二步：按关注点拆分**
将规则按主题拆分到 `.claude/rules/` 目录：
```
.claude/rules/
├── coding-style.md      # 编码风格
├── testing.md           # 测试规范
├── git-commit.md        # 提交信息规范
└── architecture.md      # 架构决策
```

**第三步：验收**
用 `/memory` 命令验证每一条规则是否被 AI 正确理解和执行。

**核心思想**：根文件是精炼的索引（常驻上下文），rules 是按需加载的模块。这与分层加载、按需检索的 Context Engineering 原则完全一致。

> CLAUDE.md 写到几百行，再加东西只会让它越用越蠢。—— 反直觉但真实：信息越多 AI 越容易迷失。

## System Prompt 的动态组织

Claude Code 展示了 System Prompt 的高阶管理方式：**动态拼接 + 缓存友好**。

### 多 text block 结构

Claude Code 的 system prompt 不是单一字符串，而是由 110+ 个独立片段文件根据运行时环境动态组装：

```
system: [
  {type: "text", text: "计费头信息..."},    // 可缓存
  {type: "text", text: "角色定义..."},       // 可缓存
  {type: "text", text: "主要 system prompt..."} // 动态内容
]
```

多 text block 的好处：
1. **灵活拼接** — 像拼乐高一样组合不同段落
2. **缓存友好** — 前几个 block 不变时可复用 Prompt Caching

### CLAUDE.md 注入机制（误区澄清）

**普遍误区**：CLAUDE.md 被拼接在 system prompt 里。

**实际机制**：CLAUDE.md **从不进入 system prompt**，而是以 `<system-reminder>` 形式在 user message 中动态附加：

```
User Message 结构：
├── <system-reminder> Skills 列表
├── <system-reminder> CLAUDE.md 内容（三级拼接） + 当前日期
└── 用户真实提问
```

**为什么这样设计？**
- system prompt 在会话创建时固定，修改则 Prompt Caching 失效
- CLAUDE.md 可能动态变更，user turn 注入更灵活
- 会话压缩后重新注入 system-reminder，CLAUDE.md 不会丢失

三级 CLAUDE.md 层次：
```
~/.claude/CLAUDE.md            # 用户级全局配置
项目根目录/CLAUDE.md            # 项目级
项目子目录/CLAUDE.md            # 模块级（父子目录拼接）
```

> "Prompt Caching Is Everything" — Thariq (Anthropic)

这一设计印证了上下文工程的核心思想：**把上下文当资源管理，缓存策略决定架构选择。**
